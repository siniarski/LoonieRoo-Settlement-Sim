- **2026-11-10, the grid in chunks: memory follows what was generated, every outcome unchanged.** The grid lived whole in memory as full-size per-tile lists (3.6 GB of the 4.4 GB after `createWorld` at 10,000) and a save there spent 0.6 s scanning bare chunks. Done in stages on branch `claude/grid-chunks-43fa71`, one commit each: the design, a sweep of every layer access through `Grids` with storage unchanged, the storage swapped to 32 x 32 chunk slots, then everything else that was sized by the map (which turned out to be the larger part: rooms, reachability and path scratch). A new 10,000 world is now 28 MB and its first tick 15 ms (it was 4.4 GB and 11.9 s). Unloading (stage 5) is a written plan, not built. Design, tables and the plan: docs/worldplan-regions.md "The second job", "The grid in chunks: built", "Unloading chunks".
  - **Why / what was tried.**
    - *The sweep (stage 2).* The six layers (tiles, ground, explored, dirt, damage, edges) became internal fields under their JSON names, so the compiler listed every straggler (312 errors in the sim; the tests, harness and game can't see them at all). A script rewrote the regular forms (`Js.Get(grid.tiles, i)` to `Grids.tileAt(grid, i)`, `grid.edges[e] = k` to `Grids.putEdge`...), by index where the old code was by index, so off-grid behaviour is the same; the rest by hand. Dumps identical, profile unchanged.
    - *The swap (stage 3).* `GridLayers.cs`: a layer is an array of chunk slots, null where every tile holds the layer's fill, allocated on the first write of another value; bytes for five layers (a tile kind is a code), doubles for damage. JSON is the flat array it was (a converter per layer; `Grid.OnDeserialized` cuts it up). Green first time; dumps, saves and bug reports the same bytes. Memory after `createWorld`: 2048 211 to 60 MB, 10,000 4,389 to 794 MB. The 794 was not the grid.
    - *What the grid was hiding (stage 4).* A new harness, `big world` (make, tick 200, walk 6 chunks, save, load, with heap and time after each), showed a played 10,000 world still at 3.9 GB, its first tick 9 s and a tick 15-20 ms. The profile at 10,000 put 95% of the tick in `BodyMod.updateBody`, which was the first caller of `Rooms.getRoomMap`: `updateRooms` copied a label for every tile of the map (400 MB) at every wall or door change, and `computeRooms` flooded all 100 million tiles. Rooms now keep labels in copy-on-write chunks and work rooms out from the tiles with something on them. Then reachability (an int a tile a mover, built by flooding every chunk: a bare chunk is now one component, never flooded), A*'s four map-sized arrays (2 GB, zeroed at the first path) and nearestTile's two (800 MB): chunks allocated where a search goes. After that: heap 28 MB after `createWorld`, 43 MB played, first tick 15 ms, peak working set 259 MB (13.5 GB before).
    - *The save.* A bare chunk is answered from the layer's fill (no tile read): the 0.6 s went with stage 3, leaving 145 ms, nearly all of it the save's picture reading every tile's explored flag; it now looks only at chunks holding a seen tile. 10,000: save 581 to 10.8 ms, load 1,043 to 66 ms, a bug report's start 571 to 10 ms.
    - *Telling a few percent apart.* Whole ticks on this shared machine spread 5-15% between runs, and the profile's first pass (allocation sampler on) disagreed with its own replay pass. A third harness, `micro`, times each reader alone on one state (best of 7), built against the old grid and the new. It found three real regressions (nearestTile +12%, a window-frame check +15%, reachability's update +7%) and they were fixed: edges read by their two tiles instead of by splitting an edge index (`edgeBetween(..., out kind)`, `seesBetween`, `edgeAt`), the flood reading a chunk's own edge array, the queue in a local. Tried and not needed: replacing the index's division with a reciprocal multiply (the (x, y) forms avoid it where it mattered).

  - **Decided.** The layers are reached only through `Grids`; the tile index and JSON are unchanged; a layer holds bytes (a ground or edge kind outside 0..255 throws at the write; nothing in the tests or a generated 2048 writes one). Room labels: a tile in a chunk never labelled reads as outdoors if floor, not floor otherwise, from the grid as it is now. `MAX_TRACKED` is 65,536 (was 2,048). Rooms' and sight's caches are weak tables (the JsMaps kept every grid and state alive). `computeRoomsWhole` stays, for the tests. docs/decisions.md "The sim's foundations" has these.
  - **Left.**
    - Unloading: a generated chunk is 51 KB, of which the grid's layers are 2.5 KB and furniture with its index 48 KB (`chunk cost`). It needs furniture per chunk with a history-free order, and an active region, before it is safe; trees out of `Furniture` (four fifths of the pieces) would cut a chunk to about 12 KB without it. The plan is in the doc.
    - At 10,000 a region's plan (about 1.5 s) is made inside a tick the first time the sim asks beyond the start's region (twice in the harness's first 230 ticks): the sim's askers should use `PlanSoon` as the far field does, or `planStart` should reach further.
    - Reachability still unites every chunk's components at each walkability change (0.33 ms for six movers at 512; it grows with the chunk count): per-chunk versions or a hierarchy. Room indexes are places in an ordered list, so a room built early in tile order renumbers every later one.
    - A save hashes every generated chunk (about 60 ms at 2048 fully generated, perhaps 1.5 s at a fully explored 10,000): a per-chunk "touched since made" mark needs furniture's writes to go through one place.
    - The game's map screen and minimap build an image of the whole map (`godot/Ui/WorldMap.cs`, `Minimap.cs`): 100 million pixels at 10,000. Not touched.
