- **2026-11-10, the tick made faster, every outcome unchanged.** docs/open-work.md "Speed" had the C# tick at about half V8's speed on 512 worlds and 2-3x slower on colonist-heavy small worlds, suspecting the JS-style list helpers. Profiled with what is in the repo, then fixed the biggest items one commit each (13 commits, branch `claude/tick-speed-cc236b`). The horde tick is 2.4x faster, crowded colonies 1.7-2x, and allocation per tick is 3-6x lower.
  - **How it was measured (no profiler installed).** A new harness test, `profile` (cs/Harness/Profile.cs), replays Tick.tick step by step with a clock and `GC.GetAllocatedBytesForCurrentThread` around each system call, each survivor's steps and `behave`'s steps (summed over survivors). `DEEP=zombies` breaks down Zombies.updateZombies down to each zombie's steps. It also samples allocations by type in process (the runtime's GCAllocationTick events through an EventListener: about one sample per 100 KB, with type names; closure classes name the method's class). `jobs probe` times reconcileJobs's parts on one fixed state. Scenes: `512` (bench's 512 world, 3 colonists), `horde-512` and `colony-512` (the stress scenes), `colony-128` (100 colonists), `mixed-128` (50 colonists, 200 zombies); 20 warm-up ticks, then 300. The whole-tick figures are measured first; the step-by-step replay runs the same ticks on a second build.
  - **The profile on main (ms a tick / KB a tick).** horde-512: Zombies.updateZombies 2.12 / 2714 (66%), Jobs.reconcileJobs 0.44 / 409, Animals.updateAnimals 0.31 / 451. colony-512: Zombies 0.96 / 1073 (61%), reconcileJobs 0.16 / 265, BodyMod.updateBody 0.12 / 257, Animals 0.12 / 229. colony-128: BodyMod.updateBody 0.09 / 251 (28%), Animals 0.05 / 180, reconcileJobs 0.05 / 165, Fog 0.03. By type, the top allocation everywhere was Js.Iter's iterator object and empty `List<Zombie>`s: `zombiesWithin` and `pushApart` made `?? []` for every empty tile they looked at (a rabbit's or a survivor's panic check scans up to 169 tiles), each with an iterator. Then JsMap/JsSet's linked-list nodes, reconcileJobs's fifteen `Js.Set(jobs.filter().map())`, chooseJob's full sort of every open job, Fog's string of every open door per survivor per tick, and craftStock's set rebuilt per craftable.
  - **The fixes, in order (each its own commit; allocations are exact, times noisy).**
    1. `Js.Iter(list)` returns a struct with a struct enumerator (same semantics: by index, length read each step). zombiesWithin and pushApart skip missing tiles instead of iterating a new empty list. colony-128 729 -> 237 KB a tick, horde 3944 -> 2011 KB.
    2. JsMap and JsSet keep insertion order in arrays with holes instead of a LinkedList (same order, same copies when listed). `HashSet.has` extension.
    3. reconcileJobs's sets as plain HashSets, one pass each (horde 0.43 -> 0.27 ms).
    4. Zombies: plain dictionaries for buckets that are only looked up; survivorsNear marks the tiles within 2 of any survivor when the dead outnumber the buckets, and pushApart lists each survivor, dog and animal under the tiles within 1 when the dead outnumber them: one lookup per zombie instead of 25 or 9. The reach check without a list or closures (0.71 -> 0.22 ms in the horde).
    5. Tick: movers' `was` and `syncStep` over their own lists, not a combined copy (two 2,000-item lists a tick in the horde).
    6. An occupancy bitmask (64K hashed bits) in front of the zombie buckets: a clear bit skips the dictionary.
    7. chooseJob: open jobs nearest first off a binary heap (same keys), popped until MAX_CANDIDATES pass the filter, instead of sorting and filtering all 1,879 guard jobs per job type (updateWork 69 -> 34 KB a tick).
    8. reconcileJobs: all fifteen sets from one pass over the jobs (no job a pass adds is one a later set takes, so they come out the same). Horde 0.97 -> 0.27 ms on the probe's state.
    9. Zombie buckets as chains in one array (a copy of the list and a next-in-tile link) instead of a list per tile; `enter` and `walkLine` work tiles out as integers instead of making Points.
    10. Fog: the per-survivor memo compares fields and an array of open doors replaced only when it changes, not a string of every door (a ConditionalWeakTable now: the JsMap kept every SimState alive).
    11. wantedCrafts builds the set of what's wielded and worn once per call, not once per craftable: colony-128 reconcileJobs 0.137 -> 0.018 ms.
  - **Tried and dropped.** A thread-static "last list" cache in Lookup.findById made lookups slower (0.075 -> 0.14 ms for 1,937 zombie lookups): the ConditionalWeakTable is faster than the thread-static read here. Reverted.
