# NOTES.md

Decisions log. Read this at the start of each session. After any non-trivial experiment, add: what was tried, what happened, what was decided.

## Project context (from initial planning)

- **Goal:** a learning and exploration project, not a shipping product. If it proves fun, port to another engine later for better platform support. Optimise for iteration speed and a good developer feedback loop.
- **Developer background:** a decade of software engineering, very little game dev (one Unity game, one simple Godot POC).
- **Game concept:** a macro-scale, 2D grid settlement survival sim. Inspirations: SimCity (emergent cities), Project Zomboid (emergent disasters), State of Decay (base and survivor management), Prison Architect and RimWorld (designation and job systems).
- **POC focus:** find or claim houses, designate rooms and their purposes (housing, mess hall, barracks, weapon storage), and either let the settlement self-organise (auto-planner) or micro-manage placement and cleanup. Each survivor has per-job-type priorities (scavenging, cleaning, zombie defence, etc.).
- **Core tension to preserve:** bigger settlement produces more, but a bigger perimeter is harder to defend. Tight fortress vs. risky expansion.

## Decisions so far

| Decision | Choice | Reasoning |
|---|---|---|
| Platform | Web | Fastest feedback loop, easy for an agent to run and inspect |
| Language / tooling | TypeScript, Vite, Vitest | Agents are strong in TS; HMR for instant feedback; headless sim tests |
| Renderer | Canvas 2D, top-down | Readability matters more than prettiness when debugging job queues. PixiJS is a possible later swap |
| Isometric / 3D | Deferred | Projection is purely a renderer concern; sim stays in grid coordinates |
| Engine (Godot etc.) | Deferred | Port later if the game earns it; the sim test suite becomes the port spec |
| Sim model | Pure, deterministic, fixed tick (default 10/sec) | Enables headless runs, replayable bugs, trivial speed controls |
| Automation model | Auto mode is a planner that emits the same designations the player does | Build manual first; auto is a layer on top, not a separate system |
| Zombies | Late milestone, crude at first | The base-building loop must be fun on its own |
| Replays | Seed + initial state + `{tick, command}[]` log | Falls out of determinism; bug reports become files |
| RNG | mulberry32, state is a single uint32 in sim state | Tiny, fast, trivially serialisable |
| Path/room invalidation | One `walkabilityVersion` counter | Simplest thing that works; refine if too coarse |
| Doors | Always walkable; act as room boundaries for flood fill | Locking/factions deferred |
| Hauling v1 | One item, one carrier, no stacks, no stockpile filters | Hauling multiplies edge cases |
| First room purposes | Housing (N beds), storage (designated area only) | Enough to exercise the requirements loop; mess hall waits for needs |
| Stuck-state thresholds | Max 600 ticks on one job; max 20 idle ticks with a doable job | Starting values, tune later |
| State mutation | Sim functions mutate the state they are given; `cloneState` (JSON round trip) when a copy is needed | Simpler than immutable updates; determinism doesn't need immutability. Replays clone the initial state first |
| Command log contents | Only commands that changed state are logged (not rejected ones, not no-ops) | Drag-painting over existing walls would otherwise flood the log; skipped entries change nothing on replay |
| View state | Camera, tool, hover, speed, pause live in `ui/view.ts`, never in sim state | Saves and replays stay free of UI concerns |
| Hot reload | `main.ts` self-accepts; on dispose it stashes sim + view state in `import.meta.hot.data` and tears down the app (RAF, listeners, HUD) | Editing any module (sim, render, ui) swaps code without losing the map you're building |

| Designations | Wall/Door tools place blueprints (1 wood each: haul, then build). Remove marks a wall/door; removing refunds the wood. Cancel tool (5). Shift = instant (old behaviour) | Gives hauling a purpose; instant mode kept for sandboxing |
| Build rules | Blueprints only on empty floor (to turn a wall into a door: remove, then build). Completing a wall evicts survivors and items on that tile | Simple and never traps anyone |
| Job queue | Derived from the world by `reconcileJobs` at the start of each tick: one job per blueprint (haul while it needs material, then build), one clean job per dirty tile. Invalid jobs are dropped and their worker released | Event-driven job creation would drift out of sync; a linear reconcile can't |
| Job choice | Highest-priority type first (ties: build, haul, clean), then nearest job of that type (Manhattan) that is actually doable, checking up to 8 candidates. Idle with nothing doable: retry every 5 ticks | Matches CLAUDE.md; the cap and back-off bound per-tick pathfinding cost |
| Reachability | Connected-component labels cached per grid + walkabilityVersion (WeakMap, outside sim state) | Unreachable candidates cost O(1) instead of a failed A* that floods the map |
| Default priorities | 3 / 3 / 3 for build / haul / clean | Neutral start; type order breaks ties |
| Direct orders | A move order releases the survivor's job (dropping any carried item); they go back to work after arriving | Proper drafting can come with the threat milestone |
| Dirt | 1/30 chance per step onto floor, via the sim RNG (drawn on every floor step, so RNG use doesn't depend on dirt) | Gives cleaning a steady trickle; deterministic |
| Invariant checker | `sim/invariants.ts` cross-checks survivors/jobs/items/blueprints; tests run it every tick, the debug panel shows it live | Turns "two survivors on one job" style bugs into a red test |
| Rooms | Derived by flood fill over floor (walls and doors are boundaries); regions touching the map edge are outdoors. Memoised per grid + walkabilityVersion, outside sim state | Recomputed only when walls/doors change; nothing to keep in sync |
| Room purposes | Stored as designations anchored to a tile; apply to whatever room contains the anchor. Built-over anchors slide to a neighbouring floor tile; when rooms merge the older designation wins; an anchor that ends up outdoors is kept and shows "not enclosed" | Survives remodelling (e.g. remove a wall, then build a door) without the player redoing it |
| Requirements | Both: enclosed, has a door. Housing: ≥1 bed, ≥4 tiles per bed. Storage: ≥4 tiles | Small and visible; first unmet one is shown on the room label |
| Beds | Furniture (`state.furniture`), built from a blueprint with 1 wood, walkable, items can't be dropped on them. Remove refunds the wood | Housing needs something to require; beds were due in milestone 6 anyway |
| Storage | Complete storage rooms are haul destinations: each loose item outside storage gets a store job; destination tile chosen and reserved at claim time. Builders take wood back out of storage | Answers the M4 stockpile question with the existing haul job type |
| Cleaning scope | Indoors only (any enclosed room): dirt is only tracked indoors, clean jobs only for indoor dirt | Answers the M4 home-area question; no more scrubbing the street |
| Cancel tool | On a blueprint cancels it; otherwise clears the purpose of the room under the click | One "undo a designation" tool |
| Rest and sleep | Integer rest 0-2000, drains 1/tick awake (tired below 500, ~2.5 min at 1x). Tired survivors drop their job (via releaseSurvivor), reserve the nearest reachable free bed, sleep until full. Bed +4/tick (~37s), floor +2/tick (~75s) when no free reachable bed. Survivors start at 100/85/70/55% by index (no RNG). Bed gone / path blocked → re-plan or floor, never stuck. A direct order wakes them. `setRest` debug command | Sleep first, hunger later. Integers keep it exactly deterministic; stagger avoids everyone tiring at once. Single drain rate for now (no faster drain while working) |
| Hunger and food | Food is an item (`f` in maps, tin cans on screen), stored like any item, never used for building. Satiety 0-3000 drains 1/tick always (hungry below 750, ~3.75 min at 1x). A hungry survivor with reachable free food drops their job, reserves the nearest food, walks to it and eats it in place (30 ticks, +2000). No food: keep working, look again every 20 ticks. Eat before sleeping; sleepers aren't woken to eat. Debug commands `setSatiety`, `spawnFood` | "Keep it simple at first": mirrors sleep, reuses item reservation, no mess hall or carrying food |
| Scavenging | Ruins hold crates (`c` in maps, furniture with 5 loot). The Scavenge tool (Orders, 1) drags a box; every crate with loot in it is marked. Marked crates get one scavenge job each (new job type, own priority column, tie order build > haul > scavenge > clean): search from an adjacent tile for 40 ticks, drop one find (food 60% / wood 40%, sim RNG), repeat until empty, then unmark. Finds are brought home by the existing store hauling; without storage they stay at the ruin. Cancel unmarks; Remove dismantles a crate for wood | Answers "where does food come from" with the systems already there; RNG keeps it deterministic |
| Day/night | Clock derived from the tick (nothing stored): 200 ticks/hour, 4800-tick day (8 min at 1x), start 06:00, night 21:00-05:00 with 2 h dusk/dawn fades. At night survivors go to bed below 75% rest instead of 25%. Dark overlay over the world (not survivors or labels); clock in the top bar | Sleep gets a natural rhythm; zombies will need "night" |
| Health and death | Health 0-1000. Starving (satiety 0) costs 1/tick (~100 s to die from full); +1/tick asleep, +1 per 5 ticks awake and fed. At 0 the survivor dies: job, carried item, bed and food are released, they're removed after the survivor loop (never spliced mid-iteration), and "X died of starvation/injuries" goes to the event log | Gives hunger teeth; zombies will deal damage through the same path |
| Event log | `state.events` (capped at 50), shown as a feed under the status line | Generic: deaths now, attacks later |
| End-of-tick reconcile | Room anchors and needs (beds/food) are reconciled at the end of each tick as well as the start | Work finished mid-tick (wall on an anchor, bed dismantled under a sleeper) must not leave dangling references between ticks; the fuzz test caught both |
| Zombies (M7, crude) | Night N brings 1 + N zombies (2, 3, 4, ...; was 3 + N until the player found 4 on night one too much), spread evenly through the night (night 1: 23:00, 03:00), each on an outdoor map-edge tile (sim RNG, not within 8 of a survivor); a "Night N falls: K zombies expected" notice at 21:00; at most 20 alive at once (safety cap). They walk floor only (doors stop them: CLAUDE.md door rule revised), 6 ticks/tile, chase the nearest reachable survivor (re-plan every 15 ticks), hit adjacent survivors for 40 every 10 ticks, wander when nobody is reachable, all leave at dawn. Zombie damage uses health; deaths say "died of a zombie attack" | Night pressure that rewards enclosing the base; dawn retreat keeps it crude |
| Guards | New `guard` job type, one job per zombie, first in the tie order. Guards close in and hit for 50 on arrival, then every 10 ticks (4 hits kill). Needs never pull a survivor off a guard job; nobody goes to bed with a zombie within 10 tiles; a hit wakes a sleeper | Without the guard-duty rule a tired guard flip-flopped between hunting and bed as the zombie drifted across the danger radius (the fuzz test caught it) |
| Farming | Farm area tool (Rooms, 3) lays plots on bare floor. New `farm` job type (tie order guard > build > farm > haul > scavenge > clean): stand on an empty plot to sow (20 ticks), it grows for 2400 ticks (half a day), then harvest (20 ticks) drops one food on the plot and it gets re-sown. Building a wall or door on a plot removes it; Cancel removes plots. ~4 plots per survivor keeps up; 12 plots fed 3 survivors through 3 days with surplus | Renewable food with the existing job, haul, and eat systems; outdoor fields are exposed to zombies |
| Auto-planner (M8) | `planFurnish(state, x, y)` in sim/planner.ts is pure: it returns ordinary commands plus notes, and the Furnish tool (Rooms, 4) applies them through applyCommand, so the log holds plain designateBuild commands and replays need no planner. Housing: one bed per survivor minus beds in other housing, at least 1, capped by capacity (1 per 4 tiles), existing beds/plans counted; spots are empty floor not next to a door, most walls first. Storage: nothing to add. Unfixable problems (no door, not enclosed, no purpose) are explained instead. Notes show as a 6 s message under the status line | CLAUDE.md: "the auto-planner is just another source of designations" |
| Injuries and medicine | Health tiers: above 60% normal; 30-60% hurt (5 ticks/tile instead of 4, work and guard blows at 3/4 speed); below 30% critical (drops any job, even guarding, and goes to bed, zombies or not). Sleepers stay in bed until rested *and* back to 60%, but always wake when hungry (a starving sleeper would lose health instead of healing). Bandages (`m`, a scavenge find: food 50% / wood 35% / bandage 15%) are fetched and applied by hurt survivors like a meal: +300 health, reserved so two survivors never go for the same one | Player pick from four candidate systems; makes zombie fights cost something without making them deadly |
| Wanderers | From day 2, one wanderer at 10:00 on an edge floor tile (sim RNG), a second at 14:00 only if beds outnumber survivors plus waiting wanderers. They wait in place; Take in (`acceptWanderer`) makes them a survivor with default priorities, Turn away (`dismissWanderer`) removes them; ignored for 3 hours or still there at nightfall, they leave. A wall built on one nudges them to a free neighbour (or they leave). Names come from their own counter (`namesGiven`, 26 names) so they no longer depend on entity ids | Player pick; growth is a choice, gated softly on beds |
| Weapons and armory | Weapons (`/`) are a scavenge find (food 45% / wood 30% / bandage 15% / weapon 10%). Anyone with guarding switched on and no weapon fetches the nearest free one *between jobs* (reserved like food and bandages; hunger or wounds cancel the errand). Equipped weapons sit in a separate `weapon` slot (item `carriedBy`, no `pos`), so hauling still works. Armed blows do 100 instead of 50 (2 hits per zombie instead of 4); a weapon breaks after 5 kills (`wear` on the item) and drops where its owner dies. New room purpose Armory (walls, door, 4+ tiles): weapons are hauled there if one is complete, else to storage, and move over when an armory is finished | Player pick; gives scavenging a reason to continue and guards something to gear up with |
| Mess hall | Tables (`t`, blueprint `T`, 1 wood, built like beds). Room purpose Mess hall: walls, door, at least 1 table. A seat is a free floor tile beside a table in a complete hall, one eater per seat (`meal.seat`). A hungry survivor picks the free seat nearest the food at the moment they decide to eat, carries the food there (`carrying` during a meal is allowed) and eats; no free seat, or the seat stops being one, means eating where they stand. The planner furnishes a hall with one table per 4 survivors, in the open and spaced apart | Player pick; makes room-building matter beyond beds |
| Mood | 0-100, 50 baseline, from timed thoughts (one per kind, a repeat refreshes): ate at a table +10 / without -5 (1 day), slept a full night in a bed +5 / on the floor -10 (1 day), someone died -15 (2 days), and -10 while hurt. Shown as a Mood column in the priority panel, with the reasons in its tooltip and the debug panel | Crude on purpose: gives tables and beds a payoff, and deaths a cost, without a full needs model |

It batters the door or wall in its way (40 per blow, every 10 ticks; doors 400, walls 1200). Damage lives in `grid.damage`, cleared whenever a tile changes. ## Open questions

- **Food is still finite overall.** Scavenging adds 25 finds (5 crates) in the sandbox, ~15 of them food. A renewable source (farm plot) or more ruins further out (risk vs reward, ties into the perimeter tension) is the next question.
- **Room labels overlap** when two designated rooms sit side by side at low zoom. Consider shortening labels or stacking them.
- **Area tools for Remove/Cancel?** Box-dragging might suit them too.
- **Zombie balance (2026-10-31, player call):** "one healthy survivor should be able to take a basic zombie". Zombie damage 60 → 40 and guards strike on arrival: a one-on-one fight now costs 12-15% health (was 23-29%), locked in by a balance test (healthy guard wins, keeps >= 80%). In the sandbox test night everyone ended at 98-100% (was 14% and 38%). Danger now comes from numbers, sleeping outside, or being caught tired/hungry; more zombies per night (or tougher variants) is the lever if nights feel too safe.
- **Sleepers outdoors** wake only when hit: kept on purpose (player call).
- **Planner scope.** Only beds so far. Next candidates: a door for a doorless room (needs remove+build of a wall tile), "plan a whole room" (walls + door + furniture from a dragged box), and auto-furnishing every designated room on a timer.
- **Farm yield may be generous.** With a 12-plot field and nothing else, the sandbox colony survived 3 days and 9 zombies with 49 food lying around. Fewer plots, slower growth, or seasonal growth could add pressure back.
- **Arming at night.** Guards only arm between jobs, and at night guard jobs come first, so a guard who never got a quiet moment by day fights unarmed. Fine for now; a "fetch weapon first" step in the guard job would fix it if it bites.
- **Seat walk.** A survivor carrying food keeps walking their path to a seat that stopped being one, and only eats on arrival (without the bonus). Re-checking each step would fix it if it looks silly.
- **Workshop room.** Crafting works at any bench for now. A Workshop room (faster crafting, or required for some recipes) is the natural next step.
- **Balance harness.** The headless balance runs use a scripted player (`zz-balance.test.ts`, kept out of the repo; it needs Node types). Worth committing properly (with `@types/node`) if balance passes become routine.
- **New survivors.** Nobody joins yet, so deaths are permanent losses. Wanderers arriving by day (with a chance to recruit) would balance it.
- **Mess hall.** Survivors eat where the food lies (often in storage). A mess hall room type (needs a table) could be the preferred place to eat, with a mood bonus later.
- **Sleep tuning.** 2.5 min awake / ~40 s in bed at 1x is set for visibility while testing; a real day/night rhythm may want longer. Should survivors prefer beds in complete housing over stray beds? (Currently any bed.)
- **Hover checklist placement.** The room checklist (top-left) can cover the label of a room in the top-left of the screen. Consider moving it next to the cursor.
- **Haul distance.** Storage far from the wood pile makes hauling slow (1 item per trip). Fine for now; if it drags, consider carrying 2-3 or a "nearest storage" preference per item.

- **Scale: "macro" vs colony.** The concept says macro-scale (SimCity), but the systems are colony-scale (individual survivors doing per-tile A*, like RimWorld). Plain A* is fine for 5-30 survivors. Hundreds of survivors on a town-sized map would need hierarchical pathfinding or flow fields. What is the target map size and survivor count?

## Dev gotchas

- **Vite's watcher can miss rapid successive edits on Windows.** Symptom: the browser keeps running old code (a `?t=` URL serves stale content) even after a page reload. Fix: re-save the file, or restart the dev server. Seen twice now (draw.ts in M3, hud.ts for the pause banner). Quick check: `fetch('/src/<file>', {cache: 'no-store'})` in the page and look for the new code. If it keeps happening, try `server.watch.usePolling` in vite.config.ts.
- **Don't fetch `/src/...` modules with made-up query strings while debugging.** Vite adds them to its module graph as separate modules with no importers, which makes hot reload fall back to full page reloads for everything they import. Restart the dev server to clear it.
- **Editing `index.html` opens a `file://` preview tab in the browser pane**, which becomes the active tab and backgrounds the game tab. Background tabs don't get `requestAnimationFrame`, so the game freezes at its current tick. Close the extra tab.
- **Stop the dev server during big multi-file sim changes** and restart it to verify. Otherwise every intermediate save is hot-reloaded and may half-apply.
- **Edits across several files are hot-reloaded one file at a time.** In-between states can throw (missing imports and so on); the frame loop now survives that. If hot reload fails outright ("Failed to reload main.ts"), refresh the page.
