## Start here (state as of 2026-11-11)

**What it is.** A deterministic survival sim: the sim in pure C# (`cs/Sim`, ~880 xUnit tests, schema 78, world generation version 2), the game in
Godot 4.6 .NET (`godot/`). It began as a RimWorld-style colony sim and is now **Project Zomboid-style survival in
first person** (3D, `godot/World3D`), with an optional colony sim run from the map screen's Colony tab (M; 2D
top-down, `godot/Render`), neighbouring settlements living their own lives, and survivors with stories and requests.
Movement is continuous, walls and doors stand on tile edges, and worlds are generated by region from the seed
(organic terrain, rivers and towns since 2026-11-10). Merged on 2026-11-11 (log/2026-11-11-01-the-big-merge.md):
the grid in chunks, faster saves and ticks, the ground's relief, buildings laid out as real places, growth,
wildfire, rain and snow, world lighting, distinct weapons and firearms, the bag as a grid with a character sheet,
clothes and hair on everyone, and new walks and zombie animation. Until 2026-11-08 it was TypeScript in the browser: git tag
`ts-final`.

**Run and check.**
- `./check.sh`: builds the sim, its tests and the game (Release, and the Debug build the game runs), runs the tests
  (about 10 s). `./check.sh --all` adds the Godot self-test. Output is in `.check/`: read it, don't rerun.
- `./finish.sh "message"` (or `-F file`; `--all` for the self-test too): runs the check and, only if it is green,
  commits everything (`git add -A`). It never pushes.
- `./shot.sh <game args>`: builds Debug, runs Godot, prints a short result (full output `.check/shot.log`). For
  example `./shot.sh --seed=3 --ticks=200 --shot=out.png`. Every game flag, the text-output ones too, is in
  godot/README.md.
- Play: open `godot/` in Godot 4.6 .NET and press Play (main menu, New game, "Who you are").

**Working agreements (the player's).**
- Push only when the player says so, every time. Commit only on a green check.
- Multi-part requests are done in this session, one piece at a time, unless the player asks for parallel sessions.
- Log every non-trivial change as a new file in `log/` (what, the numbers, what's left).
- Ask before adding dependencies (NuGet packages, Godot add-ons, tools such as dotnet-trace).
- Tone: grim, no humour. The player likes to approve a batch ("do 1-5"), then have it built and checked end to end,
  with a look at the running game (`./shot.sh`, `--selftest`) for anything visible.

**Session habits.** Keep a session to one small task. Prefer text output (tests, DebugText, the game's text and
trace flags) to screenshots unless the question is about rendering. Parallel sessions only when the player asks;
cheaper models for mechanical work.

## Open questions

- **Is solo survivable for a human?** The scripted solo player died by day 2-5 (balance pass, 2026-11-04) before hand
  tools, foraging, hunting, longer days and group-sized nights; a human playtest is the real test. Watch food (2.4 a
  day to stay fed, 0.6x loot a year on), the crude starting weapon, and the hut door at night.
- **Movement and combat feel.** Continuous movement (2026-11-05) and swings on a cooldown: does it feel right under
  WASD and in first person? Decided by playtest.
- **Colonies die in their first winter** without coops or a greenhouse (balance pass 2026-11-06: with coops, two of
  three scripted colonies are alive at day 25). The game's autumn alert now points at both. Watch whether a human
  finds them in time.
- **Infection may be too easy** for a player who uses herbs and amputation (balance pass 5: no infection deaths).
- **Scale: macro vs colony.** Per-survivor A* is fine for tens of people; hundreds on a big map would need
  hierarchical pathfinding or flow fields, an item spatial index, and an active region (docs/design.md "Big worlds").
- **Residents are still simple:** they potter, trade in person, join, or fight; no caravans, scavenging runs or
  alliances of their own.
- **Infected rising in bed** among sleepers is brutal. Move the dying to the infirmary, or have them wake neighbours
  as they turn?
- **Arming at night:** guards only arm between jobs, so one who never got a quiet moment by day fights unarmed.
- **Small UI nits:** room labels overlap at low zoom; the hover checklist can cover a room's label; Remove/Cancel
  could use box drags.

## Dev gotchas

- **Use `./shot.sh` for pictures.** The game runs the Debug build (`godot/.godot/mono/temp/bin/Debug`); `./shot.sh`
  (and the check) build it first, so a `--shot` never shows old code. Calling Godot by hand after a sim change needs
  `dotnet build godot/LoonieRoo.csproj` first.
- **`./check.sh` keeps its output in `.check/`** (build.log, tests-N.log, selftest.log): read them rather than running
  the check again with another filter.
- **Godot logs** each run to `%APPDATA%\Godot\app_userdata\LoonieRoo\logs` (the newest is godot.log): C# exceptions
  in _Process are printed there and the game carries on.
- **The self-test opens a window** and drops the real mouse's events while it runs (input accumulation off;
  moving the mouse is fine).
  Headless (`--headless`) won't do: Controls aren't laid out without a window, so clicks on the HUD miss.
- **Godot's `Time` and `Control` clash with the sim's** (LoonieRoo.Sim.Time, LoonieRoo.Sim.Control): files in godot/
  alias them (`using Time = LoonieRoo.Sim.Time;`, `using Control = Godot.Control;`).
- **XML comments can't contain `--`** (a csproj with `--filter` in a comment won't load).
- **Godot makes `.uid` files** next to scripts when the editor opens the project: commit them.
- **The old render bench** is at git tag `godot-bench-final`; if Godot's project manager still lists "EXPERIMENT
  render bench", remove it there.
- **Blender and Godot animation traps** (the Blender MCP closing Blender on a glTF import, Skeleton3D, shader-buffer
  slots): docs/open-work.md "Characters (3D)".
- The port's JS-semantics traps are in CLAUDE.md; the browser era's gotchas went with the TypeScript (tag ts-final).

## Session log

The session log is in `log/`, a file per entry: `log/YYYY-MM-DD-NN-slug.md` (NN: the entry's place in its day, one
more than that day's highest; two sessions picking the same NN is fine, their slugs differ). Add a new file for each
non-trivial change (what was tried, the numbers, what was decided, what's left); never edit NOTES.md just to log.
`ls log/` is the index; `grep -ril <word> log/` finds an old entry.
